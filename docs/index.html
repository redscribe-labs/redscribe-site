01 · Engagements

Everything about the job, in one place.

Each client project is one engagement: its scope, dates, team, checklist progress, and every finding raised against it, moving through a real status lifecycle from In Progress to Delivered and on to remediation testing.

  • Status lifecycle from In Progress through QA, Delivered, and Closed
  • Team membership with default reviewer and QA per engagement
  • Scope changes go to a Team Lead for approval, with history kept
How engagements work →
02 · Checklists

Test methodically. See what’s left.

Run OWASP WSTG or your own template against an engagement, as many runs as the scope needs. Every item records what was tested and links to the findings it raised, and RedScribe nudges you toward the checks you haven’t touched yet.

  • OWASP WSTG, or your own templates in JSON or CSV
  • Several independent runs per engagement
  • Nmap, Burp Suite, and Nuclei import straight to Draft findings
Checklists and scanner import →
03 · Findings

Write it once. Score it properly.

Findings are rich-text write-ups built from the sections your firm defines, scored with a CVSS calculator that speaks both v3.1 and v4.0. Start from an approved vulnerability catalogue entry instead of a blank page.

  • Built-in CVSS v3.1 and v4.0 calculator
  • Content sections you configure, per instance
  • A shared, QA-approved vulnerability catalogue
Writing findings →
04 · Review and QA

Nothing reaches a client unchecked.

Every finding walks from Draft through Review to QA Approved, with named assignees at each step. Reviewers leave comments anchored to the exact text they’re about, so feedback lands where it applies.

  • Draft → Review → QA, with changes requested at either stage
  • Inline comment threads anchored to highlighted text
  • My Queue shows only what’s assigned to you
The review workflow →
05 · Reporting

The report your client actually reads.

One shared model drives every export, so PDF, HTML, Markdown, and Word all render the same report. Word export fills in a .docx template you design yourself, styled with your own document’s named styles.

  • PDFwith optional password
  • Wordyour own .docx template
  • HTMLself-contained file
  • Markdownzipped export

06 · Client portal

A narrow, read-only door for clients.

Client accounts see their own released engagements and, within them, only findings that have actually cleared QA. Nothing is editable, and nothing else is visible.

  • Release an engagement to the client when it’s ready
  • Only QA-approved findings, ever
  • See which findings each client user has opened

Security and administration

Built for work that can’t cut corners.

A pentest firm’s findings are sensitive by nature, and some clients raise the bar further. These defaults were chosen with that in mind from the start.

Every request, hash-chained.

An append-only audit log covers every request, not just the ones that change something. Each entry’s hash chains onto the last, so tampering shows.

a13f…9c02#4,118
6e21…7bd4#4,119
f048…1a3ecurrent

CVSS v3.1 and v4.0.

Pick the metrics, get the vector and score. Or paste a vector you already have.

Encrypted per engagement.

Sensitive fields are sealed with AES-256-GCM under each engagement’s own data key, wrapped by your instance’s root key.

root keyRS-UMB-0369RS-INI-0412RS-CYB-0388

MFA from the first login.

By default, every local account enrols in TOTP before it can see anything. Require it per role, or sign in with Google or Microsoft.

482913

Know how fast fixes land.

Mean time to remediate by severity, severity over time, and the classifications that keep recurring for the same client.

Roles are data, not tiers.

Build the roles your firm actually has, permission by permission. No fixed Admin/Editor/Viewer ladder.

Encrypted backup and restore.

Server-side, encrypted, and restore shows you an account-state diff before anything live is overwritten.

Install

Up and running on your own box.

Four supported ways to run it: Docker Compose with automated Tailscale HTTPS, your own TLS certificate, plain HTTP on a trusted network, or local development without Docker.

Installation guide →
quickstart
# Local try-out: no TLS, no domain
$ git clone https://github.com/redscribe-labs/redscribe && cd redscribe
$ cp .env.example .env   # plus three secret files, see the quickstart
$ docker compose up -d --build
$ docker compose exec web python manage.py generate_root_key
# paste the printed key into secrets/root_key.txt, then:
$ docker compose up -d web
# open http://localhost:8000/setup/
